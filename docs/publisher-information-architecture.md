# 发布器信息架构与操作分块重组建议

> 状态：研究稿，未实施
> 日期：2026-08-18
> 适用范围：`src/signriver_publisher/` 发布器主界面、发布中心及兼容/维护入口
>
> 本文只讨论信息架构、页面分块和操作顺序，不改变代码、不删除现有能力，也不代表已经批准实施。

## 1. 研究结论

当前界面的主要问题不是按钮数量本身，而是把三种不同维度混在了同一层级：

1. **业务对象**：程序更新、游戏内容、卡带、Hub、公告、模块归档；
2. **发布阶段**：准备、核对、确认、上传、回读、恢复；
3. **风险等级**：普通发布、兼容回退、高级远端维护。

现在的顶部页签大致按“代码模块/技术对象”切分，发布中心又按“批次阶段”切分，导致同一件事被拆散。例如程序版本批次需要同时涉及三端包、更新说明、远端基线、预检、确认、双源执行和验收参考，但用户必须在多个块之间寻找这些步骤。

**核心建议：顶部只按操作者任务和风险分层；同一批次的阶段操作必须在一个连续工作区内完成。**

## 2. 重新定义主导航

建议将当前七个顶部页签收敛为五个一级工作区。一级工作区不再直接对应某个技术对象，而是回答“我现在要完成什么”。

### 2.1 发布工作台

这是默认首页，也是所有标准发布的入口。

负责：

- 当前游戏、当前发布批次和批次状态；
- 创建/打开程序版本批次、游戏内容批次、Hub/公告批次；
- 显示当前批次的下一步；
- 进入批次详情、预检、确认、执行、恢复和审计；
- 显示最近批次和失败批次。

不再把“批次历史”“远端基线”“预检确认”“执行恢复”做成互相平行的一级入口。它们都是当前批次的不同阶段或辅助视图，应当从发布工作台的批次上下文进入。

### 2.2 内容准备

负责所有本地内容和产物的准备，不直接承担远端上传。

建议包含两个明确的子区域：

- **程序包准备**：版本号、三端包收件目录、Windows/SteamOS/macOS 包、更新说明、模块归档；
- **游戏内容准备**：DLC、补丁、`catalog.json`、卡带、Hub 主表、公告。

“资源管理”“内容与卡带”“卡带管理”目前存在职责交叉，建议整合为该工作区中的子页面或子标签。用户先在这里准备内容，再从“发布工作台”把已准备内容纳入批次。

这里可以提供：

- 扫描/刷新目录；
- 替换单个平台包；
- 编辑更新说明；
- 生成或查看本地快照；
- 创建对应类型的发布批次。

这里不提供直接上传、远端删除或采用远端附件，避免准备动作和远端副作用混在一起。

### 2.3 核对与验收

负责“发布前确认依据”，但不负责真正上传。

建议包含：

- 远端基线读取；
- 本地与远端差异对照；
- 机器预检；
- 更新说明与版本核对；
- 人工验收记录和快照；
- 最终确认摘要。

其中人工验收是参考信息，不是发布硬门禁。它可以附加到当前批次，也可以标记通过、失败或跳过，但不能阻塞标准发布流程；真正阻塞发布的仍是版本、平台、架构、包结构、哈希、模块归档和双源配置等机器检查。

如果从批次进入该工作区，页面应自动带入批次，不要求用户重新选择版本、目标源或文件。

### 2.4 执行与恢复

负责所有已经确认后的远端动作：

- 双源上传；
- 附件回读；
- 清单最后切换；
- 最终清单回读；
- 安全暂停；
- 重启后恢复；
- 部分源失败后的补齐；
- 操作审计导出。

它必须始终显示当前批次，不应该允许用户在执行过程中随意切换到另一个批次。批次历史、阶段进度、失败原因和下一步恢复建议应在同一页面呈现。

### 2.5 高级维护

只放高风险、低频、可能绕过标准批次流程的动作：

- 兼容界面的单源发布；
- 双源镜像回退；
- 远端附件删除；
- 采用远端附件；
- 单源清单修复；
- 仓库/令牌/发布目标维护；
- 读取历史兼容发布状态。

这些操作必须明确显示“这是高级维护，不是标准发布”，并要求关联一个批次和精确确认文本。不能让它们与普通的“准备包”“运行预检”处于同一视觉层级。

## 3. 一个发布批次应当如何组织

无论是程序更新、游戏内容还是 Hub/公告，都建议统一使用下面的连续结构：

```text
选择发布类型
  → 准备输入
  → 读取远端基线
  → 运行机器预检
  → 查看集中确认摘要
  → 执行双源上传
  → 回读附件与清单
  → 完成 / 暂停 / 恢复 / 进入高级维护
```

### 3.1 批次首页

批次首页只显示用户最关心的内容：

- 批次名称和类型；
- 版本或游戏范围；
- 当前状态；
- 两个源是否已配置；
- 三端/资源数量；
- 当前阻塞原因；
- 明确的“下一步”按钮。

“创建批次”必须具备幂等保护：同一输入连续点击不能无提示地产生多个空批次。若存在未完成的同类型批次，应优先提示“打开现有批次”或要求用户明确创建新的批次。

### 3.2 批次阶段导航

阶段导航应采用固定的横向步骤条或左侧步骤栏，而不是六个互相独立的卡片：

```text
① 准备  →  ② 核对  →  ③ 确认  →  ④ 执行  →  ⑤ 回读
```

每个阶段显示：

- 已完成 / 当前 / 未开始 / 失败 / 已跳过；
- 阶段摘要；
- 进入该阶段的按钮；
- 失败时的恢复建议。

“批次历史”应作为固定的历史抽屉或侧栏，不应占据一个与“预检”“执行”并列的一级模块。

### 3.3 业务类型只在批次创建时选择

程序更新、游戏内容、Hub/公告是发布类型，不应在执行过程中分别散落到不同页签。创建批次时选择类型，随后所有页面根据批次类型显示对应字段：

| 发布类型 | 主要输入 | 最后切换的索引/清单 |
| --- | --- | --- |
| 程序更新 | 三端全量包、模块归档、更新说明 | `update-manifest.json` |
| 游戏内容 | DLC、补丁、资源快照 | `catalog.json` |
| Hub / 公告 | 卡带快照、公告、Hub 主表 | `cartridges_index.json` / `announcement.json` |

共同的阶段、状态、暂停、恢复和审计组件不应因业务类型重复实现。

## 4. 当前功能的建议归位

| 当前功能 | 建议归位 | 说明 |
| --- | --- | --- |
| 发布中心主页 | 发布工作台 | 保留为默认入口，改为批次总览 |
| 收件与准备 | 内容准备 → 程序包准备 | 负责三端包、版本、更新说明和模块归档 |
| 批次历史 | 发布工作台固定历史栏 | 不是独立业务模块 |
| 远端基线 | 核对与验收，或批次的“核对”阶段 | 与预检、确认放在同一上下文 |
| 预检与确认 | 核对与验收，或批次的“确认”阶段 | 形成一个集中摘要 |
| 执行与恢复 | 执行与恢复，或批次的“执行”阶段 | 上传、暂停、恢复、审计放在一起 |
| 资源管理 | 内容准备 → 本地资源 | 只处理工作区内容和远端配置读取 |
| 内容与卡带 | 内容准备 → 游戏内容 | DLC、补丁、Hub、公告、卡带入口统一 |
| 卡带管理 | 内容准备 → 游戏内容 → 卡带 | 不再作为独立顶层页签 |
| 验收中心 | 核对与验收 → 人工参考 | 可独立打开，但必须能附加到当前批次 |
| 构建与发布（兼容） | 高级维护 → 兼容发布 | 标记为回退/修复入口，不作为默认流程 |
| 高级维护 | 高级维护 | 保留远端删除、采用附件和单源修复 |

## 5. 页面视觉与交互建议

### 5.1 首页只保留一个主任务

截图中的“当前发布任务”方向是正确的，但应进一步强化：

- 顶部只显示一个当前批次；
- 右侧只有一个主按钮“继续当前批次”；
- 如果没有批次，显示“开始一次发布”；
- 其他内容以次级入口呈现，不与主任务竞争。

### 5.2 不要用六个同权重卡片表达一个线性流程

当前“收件与准备、批次历史、远端基线、预检与确认、执行与恢复、操作顺序”六块看起来像六个互不相关的功能。建议改为：

- 主区域：当前批次的阶段进度和下一步；
- 左侧：批次历史；
- 右侧：当前阶段内容；
- 底部或折叠区：操作顺序说明、审计摘要和帮助。

### 5.3 关联操作使用“上下文入口”而非跨页寻找

例如：

- 在程序包准备完成后，直接显示“加入程序版本批次”；
- 在预检成功后，直接显示“查看确认摘要”；
- 在人工验收记录完成后，直接显示“附加到当前批次”；
- 在远端基线读取完成后，直接显示“与当前批次对照”；
- 在执行失败后，直接显示“查看失败阶段”和“安全恢复”。

这样用户不需要记住这些能力分别属于哪个技术页签。

### 5.4 颜色和按钮等级

- 蓝色主按钮：当前阶段唯一主动作，例如“继续预检”“确认并执行”；
- 灰色次按钮：查看、刷新、导出、返回；
- 橙色/红色按钮：暂停、删除、单源修复、采用远端附件；
- 高级维护中的破坏性操作默认折叠，避免和正常发布按钮并列。

## 6. 推荐的最终导航草图

```text
SignRiver 发布管理器
├─ 发布工作台
│  ├─ 当前批次摘要
│  ├─ 批次历史抽屉
│  ├─ 程序版本批次
│  ├─ 游戏内容批次
│  └─ Hub / 公告批次
├─ 内容准备
│  ├─ 程序包准备
│  ├─ 游戏内容准备
│  ├─ 卡带与 Hub 准备
│  └─ 本地资源 / 远端配置
├─ 核对与验收
│  ├─ 远端基线
│  ├─ 机器预检
│  ├─ 集中确认
│  └─ 人工验收参考
├─ 执行与恢复
│  ├─ 双源上传
│  ├─ 附件与清单回读
│  ├─ 暂停 / 继续
│  ├─ 失败诊断
│  └─ 审计导出
└─ 高级维护
   ├─ 兼容发布
   ├─ 单源修复
   ├─ 远端附件删除 / 采用
   └─ 仓库与凭据配置
```

这不是要求一次性重写成五个页签。可以先在现有发布中心内部实现“工作台 + 批次阶段栏”，再逐步把资源、验收和兼容能力迁入对应区域，保留旧入口作为回退。

## 7. 分阶段实施建议

### 阶段 A：先修正信息架构，不改业务服务

- 确认五个一级工作区的命名和边界；
- 确认程序更新、游戏内容、Hub/公告三种批次类型；
- 明确哪些动作是准备、核对、执行和高级维护；
- 只调整导航、入口和说明文字，不改上传服务。

### 阶段 B：建立统一批次工作区

- 把批次历史改为固定抽屉/侧栏；
- 把远端基线、预检、确认、执行和恢复放入同一个批次上下文；
- 所有阶段都显示当前批次和下一步；
- 完成、暂停、失败和恢复保持在同一工作区。

### 阶段 C：整合内容准备

- 合并资源管理、内容与卡带、卡带管理的用户入口；
- 程序包准备和游戏内容准备采用同一套“扫描—校验—加入批次”模式；
- 不改变底层目录和数据协议。

### 阶段 D：收敛兼容和高级维护

- 将旧兼容发布改为高级维护下的明确回退入口；
- 给单源发布、删除、采用远端附件增加关联批次和风险提示；
- 真实双源演练、故障恢复演练和人工 UI 验收完成后，再评估删除旧的顶层页签。

## 8. 暂不实施的事项

在信息架构确认前，暂不进行以下改动：

- 不删除任何现有页签或兼容入口；
- 不修改上传、暂停、恢复和清单切换逻辑；
- 不重新命名远端仓库、版本协议或文件格式；
- 不把人工验收改成硬门禁；
- 不把所有功能强行塞到一个超长页面；
- 不为追求“少页签”而隐藏高级维护能力。

## 9. 评审时需要回答的问题

1. 一级导航是否按“准备 / 核对 / 执行 / 维护”足够直白？
2. 程序包准备与游戏内容准备是否需要在同一页面，还是仅共享同一种操作模式？
3. 批次历史是否应固定为左侧抽屉，而不是独立页面？
4. 人工验收是否只作为核对与验收中的参考面板，并从当前批次一键附加？
5. 兼容发布、单源修复、远端删除是否全部隐藏到高级维护？
6. 是否需要保留“资源管理”作为独立配置页，还是并入内容准备底部？
