# 发布器流程化与模块化重构计划

> 状态：阶段 1～6 所有可本地自动完成的实现与回归已完成；旧入口删除与兼容清理由于真实双源演练和人工验收未完成而暂缓
> 适用范围：`src/signriver_publisher/` 及其发布工作区、专项测试和操作文档
> 制定日期：2026-08-17
> 当前正式版本：`0.1.7`；当前开发目标：`0.2.0`

## 1. 背景与判断

当前发布器的业务能力本身并非明显冗余。程序更新、模块归档、游戏内容、卡带、Hub、公告、双源上传、暂停继续和发布验收都仍有保留价值。真正的问题是这些能力长期集中在同一界面和控制器中，导致信息架构、执行状态和代码职责一起膨胀。

现状的主要信号：

- `src/signriver_publisher/ui.py` 已接近五千行，`PublisherApplication` 同时承担界面组织、线程调度、互斥、工作区读取、构建、上传、远端回读、清单切换、暂停恢复和错误展示。
- 当前六个页签主要按技术对象划分，而不是按操作者要完成的任务划分。一次正式发布需要在多个页面、按钮和对话框之间来回切换。
- 现有“一键发布”实质上是若干动作的组合入口，缺少统一批次、集中预检、阶段检查点、完整审计和重启恢复语义。
- 三个平台已经形成各自原生构建边界，但 Windows 发布器尚未把“收件、校验、汇总、双源发布”表达成明确的工作流。
- 高风险维护能力和日常发布能力处在相近的信息层级，增加误操作风险，也让普通发布路径显得复杂。

因此，本计划不把目标定义为简单“删功能”或“换皮”，而是：

1. 将发布操作从技术页签重组为任务式导航；
2. 将一次发布表示为可持久化、可预检、可恢复、可审计的受控批次；
3. 将巨大 UI 控制器拆成领域模型、应用服务、远端适配器和薄界面；
4. 保留现有能力和兼容路径，通过分阶段替换避免大爆炸重写。

## 2. 范围与非目标

### 2.1 本轮重构范围

- 发布器页面布局和导航结构；
- 程序版本、游戏内容、Hub/公告三类流水线；
- 发布批次模型、状态机、工作区持久化、预检、编排、暂停、继续、重试和审计；
- GitLink/GitHub 双源上传与清单切换的安全顺序；
- 现有构建、模块归档、卡带、验收、远端维护能力的重新归位；
- 发布器专项测试和操作文档。

### 2.2 首轮明确不包含

- 不从 Windows 交叉构建 SteamOS 或 macOS 原生包；
- 不接入远程 VM 调度、SSH 构建、共享目录监听或 CI 构建编排；
- 不改变现有客户端更新协议、模块协议、卡带协议或远端存储格式，除非后续独立决策明确要求；
- 不删除 GitLink、GitHub、增量复用、暂停继续、更新说明、模块归档、Hub、公告或验收能力；
- 不将高风险维护动作包装成无人值守自动化；
- 不在首个实施阶段大改 UI 或删除旧入口。

### 2.3 三端构建边界

- Windows 包在 Windows x64 环境原生构建；
- SteamOS 包在 SteamOS x64 环境原生构建；
- macOS 包在 macOS Intel x64 环境原生构建；
- 三端候选产物最终汇总到 Windows；
- Windows 发布器负责统一发现、指纹冻结、严格校验、双源上传、清单切换和远端回读；
- 三个平台必须使用相同版本号，并由同一个程序版本批次统一发布。

## 3. 重构原则与安全不变量

### 3.1 受控流水线，而非完全无人值守

“一键发布”表示自动完成可确定、可验证、可重试的步骤，但在真正对外发布前保留一次集中确认。确认界面必须展示范围、版本、平台、产物指纹、目标源、更新说明、硬门禁结果和人工跳过项。

### 3.2 先验证不可变输入，再执行副作用

确认发布时冻结每个产物的绝对路径、文件大小、修改时间和 SHA-256。后续执行前再次核对；任一文件发生变化，原预检结论立即失效，批次返回待预检状态，不得沿用旧结果上传。

### 3.3 数据包先就绪，清单最后切换

任何让客户端“看见新版本”的索引或清单都必须最后更新。包上传成功不等于发布成功；只有远端包存在、大小和哈希校验通过后，才允许切换对应清单。

### 3.4 可恢复不等于盲目重放

每个阶段必须声明是否幂等、如何验证已完成、失败后允许从哪里继续。发布器重启后不得假设正在执行的网络动作已成功，也不得从第一步无条件重复所有副作用。

### 3.5 机器检查是硬门禁

版本、平台、架构、包结构、文件名、SHA-256、三端一致性、更新说明、模块归档和双源配置等机器可判断项必须通过。人工验收在紧急情况下可以跳过，但必须填写原因并记录操作者确认时间；机器硬门禁不可用“人工确认”绕过。

### 3.6 高风险能力隔离

远程删除、单源发布、采用远端附件、直接编辑远端状态和其他破坏性维护操作移入“高级维护”。这些能力保留，但不得出现在普通发布主路径中，并继续要求二次确认、明确目标和详细日志。

## 4. 目标信息架构：四区任务导航

发布器主窗口改为左侧任务导航、顶部环境状态、中央工作区和底部/侧边全局任务状态的结构。用户首先选择“要完成什么任务”，而不是“要操作哪个技术模块”。

### 4.1 顶部全局状态

始终显示：

- 当前工作区路径；
- 当前正式版和本地候选版；
- GitLink/GitHub 配置与连通性摘要；
- 当前活动批次及状态；
- 全局暂停状态、后台任务数量和最近错误入口。

顶部只提供状态和导航，不堆叠具体发布按钮。

### 4.2 发布中心

职责：创建、确认、执行、恢复和查看发布批次。

建议子页面：

- 新建发布；
- 进行中的批次；
- 批次历史；
- 产物收件箱；
- 发布环境检查。

新建发布使用四步向导：

1. **范围**：选择程序版本、游戏内容或 Hub/公告；
2. **产物与配置**：自动发现候选文件，允许手动替换单个文件，填写更新说明或发布参数；
3. **预检**：集中展示硬门禁、警告和人工验收；
4. **确认**：冻结指纹，展示完整变更摘要，执行唯一一次正式发布确认。

确认后进入批次看板，不继续使用多层模态对话框串联流程。看板展示阶段、当前动作、每个源的状态、日志摘要、暂停/继续、安全重试和失败处理建议。

### 4.3 内容与卡带

职责：准备和维护要被发布的内容，但不直接承担远端切换。

建议子页面：

- 游戏内容与 DLC 资源；
- 卡带定义与客户端卡带；
- Steam 元数据与命名辅助；
- 模块归档准备；
- Hub 内容和公告草稿。

这里可以生成或检查候选产物；正式上传仍应进入发布中心形成批次，避免“编辑完成即直接上线”。

### 4.4 验收中心

职责：把发布前、发布后和跨平台验收集中呈现。

建议子页面：

- 程序包结构与平台验收；
- 模块归档验收；
- 游戏内容/卡带验收；
- 远端清单与附件回读；
- 人工验收记录。

验收结果应能被批次引用，但批次必须保存当时采用的结果快照，不能只指向一个随后可能变化的“当前验收状态”。

### 4.5 高级维护

职责：承载低频、单点和高风险操作。

包括：

- 远端资源浏览和删除；
- 单源上传或单源清单修复；
- 采用既有远端附件；
- 清单/主表的手动修复；
- 工作区迁移、批次诊断和审计导出；
- 兼容期内尚未迁移的旧工具入口。

高级维护必须清楚标注“不属于标准发布流程”，并在执行前显示影响范围和恢复方式。

## 5. 三类独立发布流水线

三类流水线共享批次、预检、状态、事件、远端提供方和恢复机制，但拥有独立的输入模型、阶段定义和清单提交策略。不得用一个充满条件分支的“万能发布函数”处理全部类型。

### 5.1 程序版本流水线

一个程序版本批次统一处理：

- Windows x64 全量更新包；
- SteamOS x64 全量更新包；
- macOS Intel x64 全量更新包；
- 当前版本模块归档；
- 两个远端源的附件上传、校验和更新清单；
- 更新说明、强制更新和最低启动器版本等元数据。

标准收件目录建议：

```text
publisher-workspace/inbox/program/<版本>/
```

建议安全顺序：

1. 自动发现三端全量包、模块归档和必要元数据；
2. 严格校验文件名、版本、平台、架构、包结构、大小、SHA-256、三端版本一致性和模块基线；
3. 预检 GitLink/GitHub 两源配置、目标 Release、权限、空间、命名冲突和网络可达性；
4. 发布并核验模块归档，但不提前切换客户端程序更新清单；
5. 向两个源分别上传三端全量更新包，并逐个回读验证远端存在性、大小和 SHA-256；
6. 只有两源所需的全部三端包均就绪后，才允许向两个源分别上传各自更新清单；
7. 回读并核验两源清单中的版本、平台条目、URL/资产引用、大小、SHA-256、更新说明和强制更新字段；
8. 生成批次完成摘要和后续人工抽检提示。

安全约束：

- 任一源的包未完全就绪时，不得切换任何源的清单；
- 清单切换开始后，一源成功而另一源失败，批次进入 `degraded`，不得标记完成；
- `degraded` 的恢复动作只重试未完成或校验失败的清单切换，不重复上传已经核验通过的包；
- 不同平台包版本不一致时必须阻断；
- 新版本发布不得复用已经上线的旧版本号承载修复。

### 5.2 游戏内容流水线

适用于 DLC/游戏内容附件、卡带资源和 `catalog.json` 等客户端可发现内容。

建议顺序：

1. 选择内容集合和目标卡带；
2. 校验本地文件、命名、大小、SHA-256、授权边界和卡带引用；
3. 计算增量差异并确认可复用的远端附件；
4. 向目标源上传新增或变化的内容附件；
5. 回读验证附件；
6. 生成新的目录快照；
7. **最后上传 `catalog.json`**；
8. 回读目录并验证其中每个引用均可解析到已核验附件。

`catalog.json` 是内容可见性开关，不能在附件之前上传。远端复用必须以已核验的文件身份为依据，不得只凭同名文件猜测一致。

### 5.3 Hub 与公告流水线

适用于 Hub 数据、公告内容及其主索引。

建议顺序：

1. 读取当前远端状态并形成基线；
2. 校验本地条目、关联资源、ID 唯一性、时间字段和展示约束；
3. 生成完整、可独立验证的新快照；
4. 上传并回读快照和关联资源；
5. **最后更新主表/主索引**，使客户端切换到新快照；
6. 验证主表引用、快照完整性和客户端可读性。

禁止边修改远端主表边逐条上传内容。完整快照先就绪、主表最后切换，才能保证失败时旧快照仍可继续使用。

## 6. 发布批次领域模型

### 6.1 核心类型

#### `ReleasePlan`

表示一次已保存的发布意图，至少包含：

- 批次 ID、类型、目标版本/内容范围；
- 创建时间、更新时间、当前状态；
- 产物列表和冻结指纹；
- 两源目标及非敏感配置摘要；
- 更新说明和发布选项；
- 预检结果快照；
- 阶段记录和事件索引；
- 人工确认、跳过原因和恢复信息。

#### `ReleaseArtifact`

表示一个本地或远端产物：

- 逻辑角色，如 `windows_full`、`steamos_full`、`macos_full`、`module_archive`、`catalog`；
- 平台、架构、版本；
- 本地绝对路径或受控工作区相对路径；
- 文件名、大小、修改时间、SHA-256；
- 远端源、远端标识和核验状态；
- 是否必需、是否允许复用及复用证据。

#### `PreflightCheck`

表示一个可重复执行的检查：

- 稳定检查 ID 和类别；
- `pass`、`fail`、`warning` 或 `skipped` 结果；
- 是否硬门禁；
- 面向用户的说明和修复建议；
- 证据摘要；
- 执行时间及适用的输入指纹。

#### `ReleaseStageRecord`

表示流水线中的阶段检查点：

- 稳定阶段 ID、显示名称和顺序；
- `pending`、`running`、`succeeded`、`failed`、`paused` 或 `skipped`；
- 开始/结束时间、尝试次数；
- 输入摘要、输出摘要和远端核验证据；
- 错误分类、是否可重试和建议的安全恢复点。

#### `ReleaseEvent`

表示追加式审计事件：

- 事件 ID、批次 ID、时间和事件类型；
- 阶段、源、产物和动作；
- 结果、错误分类和非敏感上下文；
- 触发来源，如用户、恢复流程或后台任务。

不得在事件中保存令牌、Cookie、账号密码、私有下载凭据或大段原始响应。

#### `ReleaseStatus`

建议顶层状态：

- `draft`：输入可编辑，尚无有效预检；
- `preflight_failed`：至少一个硬门禁失败；
- `awaiting_confirmation`：预检有效，等待集中确认；
- `running`：正在执行；
- `paused`：在安全检查点暂停；
- `interrupted`：上次运行非正常结束，等待恢复评估；
- `degraded`：已经产生部分对外可见状态，但双源或最终验证未完全一致；
- `failed`：无法自动恢复且未形成可接受发布；
- `completed`：全部必需阶段和远端回读通过。

状态转换必须集中管理，UI 不得直接任意写状态字符串。

### 6.2 持久化目录

建议每个批次使用独立目录：

```text
publisher-workspace/releases/<批次 ID>/
├── plan.json
├── artifacts.json
├── preflight.json
├── stages.json
├── events.jsonl
└── logs/
    └── publisher.log
```

要求：

- JSON 写入采用临时文件 + 原子替换，避免崩溃留下半个文档；
- `events.jsonl` 只追加，必要时提供压缩/导出，而不是静默覆盖历史；
- 不长期复制三端大包和模块归档，只保存路径与指纹；
- 日志和事件必须脱敏；
- schema 必须带版本号，并为未来迁移预留入口；
- 批次目录损坏时隔离该批次并给出诊断，不影响其他历史记录读取。

### 6.3 重启恢复规则

- 启动时发现原状态为 `running` 的批次，将其标记为 `interrupted`，记录恢复事件；
- 恢复前重新核对冻结产物、环境配置和远端已完成证据；
- 重新运行预检后，从“下一个安全阶段”继续，而不是无条件从头开始；
- 已上传且回读校验通过的不可变附件可跳过；
- 状态未知的上传动作先做远端探测，再决定复用或重试；
- 一源清单已切换、另一源失败时保持 `degraded`，明确展示不一致并优先提供补齐动作；
- 暂停只在声明为安全的检查点生效；正在进行的原子网络请求不强行中断，完成后再暂停；
- 用户修改任何冻结输入后，旧预检和确认失效。

## 7. 应用服务与模块边界

### 7.1 核心服务

#### `ReleaseStore`

负责批次创建、加载、原子保存、事件追加、schema 迁移、活动批次索引和损坏隔离。它不负责上传，也不依赖 Tk 控件。

#### `ArtifactCollector`

负责从标准收件目录发现候选产物、解析命名、计算指纹、识别缺失/重复文件和处理用户替换。它只生成候选清单，不执行发布。

#### `ReleasePreflightService`

负责组合通用检查和流水线专属检查，输出稳定的 `PreflightCheck` 列表。检查应尽量纯函数化，可在无 GUI 环境下测试。

#### `ReleaseOrchestrator`

负责状态转换、阶段调度、检查点、暂停、继续、安全重试和审计。它依赖抽象接口，不直接创建 Tk 控件，也不直接拼接具体 GitLink/GitHub 请求。

#### `RemoteReleaseProvider`

统一远端源能力边界，例如：

- 预检连接和权限；
- 查询、上传和核验附件；
- 上传、读取和核验清单；
- 判断远端对象是否可安全复用；
- 返回稳定错误分类和可重试信息。

GitLink 与 GitHub 分别实现该接口；不要求二者内部 API 完全相同，但编排层看到的发布语义必须一致。

### 7.2 建议代码结构

以下是目标结构建议，不要求一次性迁移完成：

```text
src/signriver_publisher/
```

### 7.3 UI 与后台任务边界

- Tk 主线程只创建和更新控件；
- 后台线程只执行服务调用，通过线程安全消息传递上报进度；
- `ReleaseOrchestrator` 不读取控件状态，所需输入必须在启动前形成不可变命令对象；
- 取消/暂停使用显式令牌和安全检查点，不依赖随意终止线程；
- 所有完成、失败和暂停回调最终回到主线程；
- 同一批次同一时刻只能存在一个执行租约，避免重复点击产生并行发布；
- 全局任务条展示后台任务，但具体阶段信息由批次看板读取领域状态，不复制一套 UI 私有状态机。

## 8. 预检与确认设计

### 8.1 通用预检分类

1. **工作区**：目录可读写、批次存储可用、磁盘空间合理；
2. **产物身份**：文件存在、大小、修改时间、SHA-256 与冻结值一致；
3. **协议**：版本、平台、架构、命名和包结构正确；
4. **一致性**：三端版本一致、模块与清单元数据一致；
5. **远端**：两源配置、权限、目标位置、命名冲突、网络和回读能力；
6. **发布策略**：更新说明、强制更新、最低启动器版本、增量复用证据；
7. **人工验收**：记录已完成项、未完成项和验收快照；它仅作为发布参考。

### 8.2 分级结果

- **硬失败**：阻止进入确认；
- **警告**：允许确认，但必须在确认摘要中显著展示；
- **人工验收缺失或未完整通过**：显示警告与快照状态，不阻止确认或执行；快照变化仍会使已有预检和确认失效；
- **信息项**：只用于解释，不影响状态。

### 8.3 集中确认内容

确认页面至少展示：

- 批次类型、版本或内容范围；
- 三端产物和模块归档的文件名、大小、SHA-256 摘要；
- GitLink/GitHub 目标；
- 更新说明和清单关键字段；
- 硬门禁全部通过的证明；
- 所有警告与人工跳过项；
- 标准发布将执行的阶段顺序；
- “确认后将开始产生远端副作用”的明确提示。

确认结果写入批次，且仅对当时的输入指纹和预检快照有效。

## 9. 分阶段实施计划

每一阶段都必须保持旧流程可用；只有新路径达到测试对等并经过人工验收后，才能删除相应旧入口。

### 阶段 0：基线固化与特征测试

目标：在拆分前冻结现有行为，防止重构过程中无意丢能力。

任务：

- 记录现有按钮、页签、对话框、后台任务和远端副作用清单；
- 为关键旧流程补充 characterization tests；
- 梳理 `ui.py` 中纯业务逻辑、线程逻辑和控件逻辑；
- 定义稳定错误分类和现有提供方适配边界。

完成标准：现有七个发布器专项测试继续通过，新增测试能覆盖准备、上传、暂停和验收的关键合同。

### 阶段 1：领域模型、批次存储和接口骨架

这是下一执行模型应优先完成的首个实施阶段，**不先大改 UI**。

任务：

- 新增核心类型和集中状态转换；
- 实现 `ReleaseStore` 的创建、加载、原子保存、事件追加和中断恢复标记；
- 定义 `RemoteReleaseProvider`、流水线阶段和编排接口；
- 实现 `ArtifactCollector` 与最小程序产物发现；
- 实现不产生远端副作用的基础预检；
- 为模型序列化、存储损坏、指纹变化和非法状态转换编写单元测试。

完成标准：所有新增逻辑可在无 GUI、无真实网络环境下测试；旧 UI 和旧发布流程行为不变。

### 阶段 2：程序版本编排器与远端适配

任务：

- 将现有 GitLink/GitHub 操作包装为提供方适配器；
- 实现程序版本流水线的阶段定义、双源包就绪门禁、清单最后切换和远端回读；
- 实现暂停、继续、重试、`interrupted` 和 `degraded`；
- 使用 fake provider 测试单源失败、请求超时、远端已存在和清单部分切换。

完成标准：无 GUI 集成测试能够证明“两个源的全部三端包未就绪时绝不切换清单”。

### 阶段 3：新发布中心

任务：

- 建立四步向导和批次看板；
- 接入标准收件目录和单文件替换；
- 集中展示预检、确认、进度、暂停、恢复和历史；
- 通过 UI 适配层调用应用服务，不把业务逻辑复制回控件事件；
- 保留旧程序发布入口作为兼容/回退路径，并明确标注。

完成标准：新发布中心可以完成一个模拟程序批次和一个受控真实测试批次；UI 线程专项测试覆盖所有回调路径。

### 阶段 4：游戏内容与 Hub/公告迁移

任务：

- 实现游戏内容流水线，确保 `catalog.json` 最后上传；
- 实现 Hub/公告完整快照和主表最后切换；
- 将内容准备功能迁入“内容与卡带”；
- 为附件复用、快照回读和索引切换失败增加测试。

完成标准：三类流水线共享批次基础设施，但不存在互相污染的条件分支或状态字段。

### 阶段 5：验收中心与高级维护迁移

任务：

- 聚合现有发布验收能力并形成可被批次引用的结果快照；
- 将远端删除、单源发布、采用远端附件等迁入高级维护；
- 所有高风险操作增加二次确认、影响摘要和审计事件；
- 提供批次诊断和审计导出。

完成标准：普通发布导航不再暴露破坏性快捷动作；旧能力没有丢失。

### 阶段 6：旧入口下线与结构收尾

前置条件：

- 新路径达到功能和测试对等；
- 至少完成一次三端候选的完整演练和一次故障恢复演练；
- 旧入口已有明确替代位置；
- 操作文档已更新。

任务：

- 删除已替代入口和重复状态；
- 将剩余巨大模块拆分到目标目录；
- 清理兼容适配器和废弃配置；
- 更新发布器指南和架构决策。

不得为了追求文件行数一次性搬迁所有代码。每次删除都要有对应替代路径和回归测试。

### 10.1 每阶段最低验证

始终运行：

```powershell
python -m pytest -q `
  tests/test_publisher_main.py `
  tests/test_publisher_workspace.py `
  tests/test_publisher_updates.py `
  tests/test_publisher_github.py `
  tests/test_publisher_announcements.py `

```

并按改动范围运行新增测试、`python -m compileall`、Ruff 和 `git diff --check`。若修改上传流程、暂停按钮、更新说明对话框或 UI 回调，`tests/test_publisher_ui_threading.py` 为强制项。

### 10.2 新增自动化测试重点

- 状态机拒绝非法转换；
- 批次 JSON 原子保存和 schema 迁移；
- 崩溃后 `running` 转 `interrupted`；
- 文件大小、时间戳或 SHA-256 变化使确认失效；
- 三端缺包、错版本、错平台、错架构或包结构异常被硬阻断；
- 任一源缺任一平台包时，两个源都不切换清单；
- 一源清单切换失败时进入 `degraded`；
- 恢复流程不重复上传已回读核验的附件；
- `catalog.json` 始终晚于内容附件；
- Hub/公告主表始终晚于完整快照；
- 暂停只发生在安全检查点；
- UI 后台线程不直接更新 Tk 控件；
- 日志、事件和 JSON 不泄露凭据。

### 10.3 人工验收重点

- 四区导航能让操作者明确判断下一步；
- 四步向导不要求在多个旧页签之间跳转；
- 批次看板清楚区分“包已上传”“清单已切换”“远端已回读”；
- 重启发布器后能看到中断批次并获得安全恢复建议；
- `degraded` 状态醒目且不能误认为成功；
- 高级维护不干扰普通发布，但仍能完成必要修复；
- Windows、SteamOS、macOS 三端原生候选仍遵守既有真实平台验收要求。

## 11. 兼容、回退与上线策略

- 新领域层先作为旁路能力加入，不接管旧 UI；
- 新发布中心初期通过功能开关或独立入口启用；
- 每次迁移只接管一种流水线或一组明确动作；
- 新路径失败时允许回到旧入口，但不得让两个路径同时执行同一批次；
- 批次 schema 变更必须向后兼容或提供显式迁移；
- 对外协议和清单格式默认保持不变，先优化内部组织；
- 旧入口删除前保留一份能力映射表和回退说明，见 `docs/publisher-compatibility-map.md`。
- 真实双源、故障恢复和 UI 对等验收统一按 `docs/publisher-refactor-acceptance.md` 执行。

## 13. 完成定义

发布器重构完成不以“新页面能打开”或“`ui.py` 行数下降”为唯一标准，而以以下结果为准：

- 日常操作者可从任务式导航完成三类发布，不需要理解所有底层技术模块；
- 每次正式发布都有可恢复、可审计的批次记录；
- 三端程序包由各自原生环境构建，并由 Windows 统一校验发布；
- 双源数据包全部就绪后才切换清单；
- 游戏内容目录和 Hub/公告主表始终最后更新；
- 机器硬门禁不可绕过，人工跳过有明确原因和审计；
- 高风险维护动作与标准流程隔离；
- UI、编排、存储和远端提供方职责清晰，可独立测试；
- 现有功能和专项测试无回退，并完成真实故障恢复演练；
- 旧入口只在新路径达到对等后分阶段移除。
