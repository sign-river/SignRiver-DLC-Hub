# SignRiver DLC Hub 决策记录

本文件只记录会影响后续任务的方案选择、原因和已放弃路线。临时进度写入 `HANDOFF.md`，操作细节写入对应专题文档。

## 2026-08-21：发布记录持久化必须串行化并容忍 Windows 短暂占用

- 上传进度回调会高频保存 `ReleasePlan`，同时界面会轮询读取同一批次。`ReleaseStore` 必须在同一实例内用可重入锁覆盖完整的多文档保存与加载，避免 Windows 读取句柄阻止 `os.replace()`，也避免读到同一批次不同代次的 JSON 组合。
- 原子写临时文件名必须每次唯一，不能只使用进程 PID；否则同一进程的并发保存会争用同一个临时文件。
- 对 `os.replace()` 的 `PermissionError` 只允许短暂、有界退避重试；持续失败仍应停止发布并保留恢复记录。不得把发布记录写入失败误报成附件读取失败或要求重新构建资源。

## 2026-08-21：内容发布记录只有在冻结产物仍一致时才可复用

- 未执行的 `GAME_CONTENT` 发布记录即使状态为草稿、预检失败或待确认，也只有在其中冻结的每个本地文件路径、大小、修改时间与 SHA-256 仍和当前发布目录一致时才可复用。
- 构建产生新文件后，旧记录必须自动跳过并创建新的发布快照；不得靠清空上传项的 Release ID 后再次捡回同一份过期记录，也不得提供“使用当前构建”按钮绕过失败状态。
- 预检对创建快照后真实发生的文件变化继续 fail-closed；本决策只消除错误复用旧快照造成的假“需要重新构建”，不降低上传前的本地完整性门禁。

## 2026-08-21：共享 Launcher DLC 目录按文件组安全交付

- 对于《奇迹时代4》这类将多项 DLC 的描述文件和缩略图平铺在同一目录的游戏，不能把共享目录作为一个 DLC，也不能按单独子目录安装。卡带以 `grouped_directory` 安装模式和 `dlc_group_search_roots=["."]` 声明此布局。
- 发布器导入 `shared_file_pairs` 时，要求每项有同名 JSON（优先识别 `.dlc.json`）和 PNG，随后为每对文件建立独立的受管源目录及发布 ZIP；客户端解压时去除受管根目录，仅覆盖共享目录内的直属文件。
- 根目录覆盖不是无限制覆盖：安装器在此模式只接受 ZIP 根下的一层普通文件，拒绝嵌套路径、链接和越界路径；安装回执记录每个写入文件及其先前内容，回滚或卸载不会影响其他 DLC 的文件对。
- 客户端的“已安装”状态以同名 JSON 与 PNG 同时存在为准；外部安装项的删除只按该描述文件推导并删除对应 PNG，永不递归删除 `Launcher/dlc`。

## 2026-08-21：游戏内容发布采用发布器级兼容保留模式

- `GAME_CONTENT` 默认仍是严格镜像：远端仅有文件必须在用户看过差异并二次确认后删除，catalog 最后发布。
- “兼容发布：保留云端仅有文件”位于构建队列，是发布器范围的统一策略，而不是某个游戏卡带的属性；批量或单项加入上传队列时读取当前值，并在创建发布计划时冻结。开启后本地新增、变更、远端附件记录和 catalog 切换完全不变，只跳过“本地缺失即删除远端附件”。
- 旧版按游戏保存的 `.content-publish-options.json` 会在启动时迁移：若任意旧游戏曾启用兼容模式，则升级后的全局默认值为开启；旧文件不再参与后续决策。
- 删除防线必须同时位于队列确认页与执行流水线：UI 不得显示或请求删除确认，流水线也必须无条件忽略已有的删除确认标记，避免旧队列记录或手工修改突破兼容模式。
- 该设置不等同于 DLC 复用信任。复用仅使用本地 SHA-256、大小、上传后记录的远端附件 ID 与当前远端附件标识；手动“信任云端 DLC”因不能持续确认云端状态而不再提供。

## 2026-08-21：内置 DLC 游戏采用“仅补丁激活”交付方式

- 新增卡带字段 `dlc_delivery_mode`：默认 `download_packages` 保持现有的 DLC 压缩包下载/发布流程；`built_in` 表示 DLC 载荷已经包含在用户安装的游戏本体中，发布端只构建 AppInfo 与补丁资源。
- 文明7标记为 `built_in`。发布器忽略其本地 DLC 工作区、禁用导入/清理入口，并在构建时清理旧 DLC ZIP 产物，避免把本体已有内容重复上传。
- 客户端仍读取同一 Release 来取得补丁资产，但 DLC 列表显示“DLC 已随游戏本体安装，无需额外下载；安装补丁后即可激活”，禁用 DLC 选择和逐项下载入口，并将主操作表述为“安装补丁并激活”。
- 该模式只改变 DLC 载荷的交付，不跳过 AppInfo、补丁下载、补丁事务、回读校验或恢复流程；未来同类游戏只需在卡带中选择相同交付方式。

## 2026-08-21：一个游戏可声明多个完整补丁目标目录

- 卡带的主 `install_relative_dir` 保持兼容；新增 `additional_install_relative_dirs`，用于同一游戏内存在多个必须替换的 Steam API / 解锁库位置。每个声明目录都写入同一套代理库、原生库与配置文件。
- 补丁安装、哈希审计、恢复前检查与移除都覆盖全部目标目录，并使用单个事务撤销日志：任一目录写入或校验失败，已修改的其余目录必须一起回滚；恢复也会先验证所有代理库未被外部篡改。
- 《奇迹时代4》默认目标为游戏根目录及 `launcher-se/resources/app.asar.unpacked/node_modules/greenworks/lib`。发布器工作区会迁移已有该游戏的卡带并将目录清单导出到客户端 Hub 卡带；额外目录仍严格禁止绝对路径、父目录跳转和重复项。

## 2026-08-21：DLC 根目录导入须匹配游戏实际层级

- `game/dlc` 这类目录若直接包含多个 DLC 子目录，必须配置为 `children_if_root`；根目录名本身不是一个 DLC，不得以 `dlcNNN_name` 单项命名规则校验它。
- 若一级子目录已经是合法的 `dlcNNN_name` 受管理名称，导入必须保留该名称和编号，不能再次自动加前缀。未编号子目录仍可按现有自动编号规则处理。

## 2026-08-21：已编号 DLC 空目录必须作为可安装目录包发布

- 已通过名称验证但目录中不存在普通文件的 DLC 仍可能是游戏安装布局要求的一部分，不能跳过或以垃圾占位文件伪造载荷。
- 发布器为这类 DLC 生成只包含目录条目的极小 ZIP（也会保留嵌套空目录）；它照常进入 catalog 与上传流程。客户端通用目录包校验、解压、安装回执和卸载都接受该 ZIP，因此安装后会真实创建空目录、卸载时也会安全移除。
- 构建仍拒绝符号链接；操作日志以“保留空目录 · 将生成可安装目录包”直出，避免后台行为不可见。

## 2026-08-21：远端目录检测与附件完整性校验分层

- 连通性测试、远端资源列表、程序/模块差异和游戏内容镜像差异只允许读取 GitHub/GitLink 的仓库或 Release 元数据；不得为获取文件列表、判断差异或关闭前的只读检查而下载 Release 附件。
- GitHub/GitLink Release 附件元数据不包含可信 SHA-256，因此游戏内容、补丁和 Hub 快照不通过“先完整下载远端同名附件以尝试复用”来避免上传；统一直接覆盖上传，并以上传后的远端附件 ID 与大小作为发布记录门禁。
- 删除附件按 Release 列表中的附件 ID 执行，并通过重新读取列表确认删除结果，不再先下载附件内容。
- 只读远端刷新不得占用发布器的关闭保护；用户可直接关闭窗口，守护线程的后续 UI 回调会被丢弃。真正写入、上传、删除和发布仍必须保留关闭保护与安全暂停。
- 远端 API 元数据请求使用短超时，避免单个检测按钮将界面挂起数分钟；发布器不读取 Release 附件，避免下载链路成为上传流程的阻塞点。

## 2026-08-21：发布后以远端附件 ID 与大小建立可信记录

- 受当前发布网络环境限制，发布器不再下载 GitHub/GitLink Release 附件进行 SHA-256 回读；上传成功后的上传响应（或仅元数据刷新）提供的附件 ID 与大小，连同本地已计算的 SHA-256，构成该次发布的可信记录。
- 后续可复用的不可变 DLC 必须同时满足：本地 SHA-256 与大小仍匹配记录，且远端同名附件的 ID 仍与记录一致。远端 ID 缺失、变更或本地文件变化时一律重新上传。可变补丁和 `catalog.json` 继续直接替换，不复用。
- 程序更新包、模块和更新清单也不再下载回读；上传门禁改为“存在、大小相符、取得远端附件 ID”。更新清单最终只核对 Release 元数据中的附件 ID 未在发布后变化。此策略降低了端到端内容校验强度，换取可在仅能稳定上传的网络中完成发布。

## 2026-08-21：双源附件上传采用结果未知恢复

- 双源中的一次网络超时、EOF 或上传响应丢失不应导致整项从头重传。每次成功上传都立即把源站、文件名、远端附件 ID 和大小写入当前阶段记录，并在安全检查点落盘。
- 重试该阶段时，程序先读取各源 Release 元数据：记录的附件 ID 仍存在且本地大小未变则跳过该源/文件，只上传缺失端。若上传调用报错但元数据已出现同名、同大小且有附件 ID 的文件，则认定服务端已成功接收，直接恢复而不重复发送。
- GitLink Release 更新对同一 Release 与同一完整附件 ID 列表是幂等操作，可有限重试；结果仍未知时保留新附件，不能立即删除，以便后续元数据恢复确认。GitHub 上传在响应丢失后也先检查同名同大小附件，再决定是否重试。

## 2026-08-20：游戏内容发布面向用户采用上传队列

- 保留 `ReleasePlan` 作为内部的可恢复发布记录和安全门禁，不再要求发布器用户理解或手动管理“批次”。
- DLC / 补丁工作流以持久化 FIFO 上传队列呈现；一个游戏在有效队列状态中只能存在一项，重启时运行项转为可继续的暂停项。
- 加入队列前必须读取双端远端目录差异并显示镜像删除清单；只有用户确认后才允许在附件校验完成后删除远端多余文件和最后发布 catalog。
- 队列失败不阻塞后续游戏；暂停队列会停止后续自动启动。上传正确性仍以双源回读和 catalog 最后发布为准。
- 手动继续也必须遵守 FIFO：不能越过仍待处理、已暂停或需重构的前序项；确认镜像删除后若远端目录发生变化，必须重新读取差异并再次确认。

## 2026-08-20：发布器安全暂停必须覆盖远端传输与回读

- 暂停不能只存在于发布阶段之间；大文件上传和上传后的远端 SHA-256 回读也必须按小块检查暂停信号。
- 网络操作的停滞超时不得沿用两分钟级别。GitLink 附件上传以 256 KiB 为可中断粒度，连接无进展时最长等待 90 秒；暂停请求会主动关闭当前连接并转为可恢复的安全暂停，不依赖停滞超时才生效。
- 完整回读校验仍是发布正确性条件，不能为提升暂停响应而删除；应缩短单次阻塞区间并将暂停下沉到回读流程。

## 2026-08-20：程序更新发布与模块归档必须同批校验和发布

- “发布包与归档”将三端更新包和当前版本模块归档视为同一发布输入；界面分别选择更新包目录与模块归档目录，不能因默认目录不同而静默漏发模块。
- 发布前必须同时通过三端更新包结构校验和模块归档版本/结构校验；模块缺失、损坏、版本不一致或在确认后发生删改时，一律使预检与确认失效，禁止开始上传。
- 更新包与模块归档分别读取其双端 Release 基线并在差异页分组展示；“发布文件”统一执行两组附件的上传和回读校验，远端旧文件仍遵守仅保留、不删除的规则。

## 2026-08-20：Windows 补丁采用发布资产的确定性部署

- Windows 游戏内容 Release 必须同时包含 `unlocker.dll`、`original.dll` 与 AppInfo；稳定资产名由卡带映射为游戏目录中的真实 DLL 文件名。
- 客户端不再用 DLL 大小、旧 `_o` 文件或用户目录布局推断原始库；补丁操作在事务中备份目标文件、写入已校验资产并逐项验证，失败回滚。
- `GAME_CONTENT` 保持附件先回读、catalog 最后发布；远端镜像删除须经过第二次确认，未确认时禁止切换 catalog。

## 2026-08-16：采用分层的上下文交接文件

### 背景

项目同时包含多平台代码、发布资产、两套虚拟机和较长的真实游戏验收链，仅依靠单个长对话容易丢失约束或重复失败尝试。

### 决定

- 永久规则保留在根目录 `AGENTS.md`；
- 稳定架构写入 `PROJECT_CONTEXT.md`；
- 技术选择和失败路线写入 `DECISIONS.md`；
- 最新任务状态写入可覆盖更新的 `HANDOFF.md`；
- 新任务必须用 Git、代码和测试重新验证交接内容。

### 影响

今后切换任务时不复制整段聊天；只迁移仍有效的目标、结论、失败路线、验证结果和下一步。交接文件不得记录凭据。

## 稳定启动器与版本化模块

### 背景

客户端需要支持模块更新、启动失败回退和全量原地更新，同时尽量减少稳定宿主的变化。

### 决定

使用 `src/signriver_launcher/` 作为稳定宿主，业务 UI 和逻辑放入 `app/versions/<version>/`，通过 `app/state.json` 原子切换活动版本并保留回退链。

### 影响

模块兼容性和 Host API 变更必须显式管理；不能把发行模块当成单一、不可回退的覆盖安装。

## `app/versions/0.1.0/` 是模块源码唯一首改位置

### 背景

多个目标版本目录容易产生分叉和漏同步。

### 决定

日常模块业务修改先写入受 Git 跟踪的 `app/versions/0.1.0/`，发布时再同步到目标版本目录。

### 放弃的做法

不直接只改 `app/versions/0.1.7/`、`0.2.0/` 等生成或发布目录，否则下一次构建会丢失修改或产生版本不一致。

## 发布资产先就绪，代码提交后默认不推送

### 背景

仓库 CI 会在 push 后从线上 GitLink 恢复模块归档并校验 SHA-256。代码和清单先推送、线上资源尚未上传时，CI 必然失败。

### 决定

可以按用户要求提交，但默认不自动推送。发布包与清单先上传并验证，只有用户明确要求“推送”或“提交并推送”时才执行 `git push`。

## 多平台包必须原生构建并精确选择

### 背景

Windows、SteamOS 和 macOS 的可执行格式、路径大小写、Unix mode、签名及补丁资产不同，错平台包可能造成不可恢复的覆盖。

### 决定

- 各平台最终冻结包在对应原生系统构建；
- 更新清单按平台和架构精确选择包；
- 没有匹配平台包时直接拒绝，不回退到其他系统包；
- Windows 发布器统一校验和上传各平台产物，但不替代原生构建。

## SteamOS 验收使用标准内核路线

### 背景

SteamOS OOBE 环境与 VirtualBox VMSVGA、Steam 启动脚本存在兼容问题。

### 决定

保留原 SteamOS 内核作为 GRUB 回退项，并安装带 `vmwgfx` 的并存 LTS 测试内核；测试环境启动 Steam 使用 `/usr/lib/steam/steam`，不使用会清空配置的 `/usr/bin/steam-jupiter`。

### 详细记录

成功步骤、下载链接和失败路线见 `docs/steamos-virtual-machine-setup.md`。

## macOS 验收使用 VMware + Apple Recovery 路线

### 背景

VirtualBox + OpenCore、`e1000e`/`e1000`、桥接网络和若干强制 Recovery 方法在本机均失败或不稳定。

### 决定

- 用 OpenCorePkg 的 `macrecovery.py` 动态获取 Apple BaseSystem；
- 将 Recovery 转为 VMDK 后由 VMware 直接启动；
- 使用 NAT + `vmxnet3`；
- xHCI、PCIe Root Port 和虚拟 USB 键鼠使用已验证 VMX 拓扑；
- 俄语 Setup Assistant 通过 Recovery 离线修改系统级语言 plist；
- 禁止再次使用会导致 EFI 循环的 `nvram recovery-boot-mode=unused` 和 `macosguest.forceRecoveryModeInstall = "TRUE"`。

### 详细记录

完整复现、资源链接、快照链和失败路线见 `docs/macos-virtual-machine-setup.md`。

## 2026-08-16：跨平台测试必须基于局部平台依赖和干净 checkout

### 背景

Windows 本地工作区曾掩盖两类问题：测试修改共享 `os.name` 后污染 pytest 进程；发布构建测试默认扫描被 Git 忽略的活动版本目录，在 Linux/macOS 的干净 checkout 中目录不存在。

### 决定

- 平台分支测试只替换被测模块自己的 `os` 绑定、平台 helper 或显式参数，不修改解释器共享的 `os.name`；
- 源码级测试显式使用 Git 跟踪的 `app/versions/0.1.0/`；
- 只有发布集成测试可以使用活动目标版本目录，并且必须在测试或工作流中先恢复对应模块归档；
- 以干净 checkout 的 Windows、Ubuntu 和 macOS CI 结果作为跨平台测试是否成立的最终判断，不以本机 Git 忽略目录存在为依据。

### 放弃的做法

- 不再使用 `monkeypatch.setattr(configured_steam.os, "name", "nt")` 一类会修改共享模块对象的写法；
- 不再让单元测试隐式依赖 `app/versions/0.2.0/`、`dist/` 或其他本地生成产物。

## 2026-08-16：DLC 安装根目录不能仅由已安装游戏的候选扫描结果推断

### 背景

Steam 路径诊断器只扫描当前已安装文件，并按目录名启发式标记“DLC / 内容候选目录”。未购买或尚未安装的 DLC 不会出现在报告中，游戏本体内部名称以 `dlc` 开头的局部资源目录也可能成为候选。工人与资源卡带曾据此把 `media_soviet/sounds/dlc3` 的父目录误判为 DLC 安装根目录。

### 决定

- 新卡带的 DLC 安装根目录必须优先依据真实 DLC 内容包、Steam depot 文件清单或实际安装验收确认；
- 路径诊断报告只用于发现候选，不作为未安装 DLC 目录结构的唯一事实来源；
- 报告必须保留实际命中路径，同时把祖先根目录和按叶子名生成的投影路径作为独立候选并明确标注“未验证”，不得用推测结果覆盖实际证据；
- 工人与资源的真实 DLC 布局为 `media_soviet/dlc1` 至 `media_soviet/dlc4`，卡带 `dlc_relative_dir` 固定为 `media_soviet`；
- 修改卡带 JSON 后必须同步发布器内置配置、默认映射、测试预期及 `cartridges_index.json` 的 SHA-256 和字节数。

## 2026-08-16：原生发布构建必须预检版本元数据

- `tools/build_native_release.py` 在运行 PyInstaller 前校验 `LAUNCHER_VERSION`、`app/state.json.active_version` 和活动模块 `module.json.version` 一致。
- 活动版本目录缺少 `module.json` 或版本不一致时必须立即失败，不能继续生成外观正常但无法可靠启动/更新的包。
- 构建工具之间使用从仓库根开始的包导入，避免仅在特定当前目录下可用的同目录隐式导入。

## 2026-08-16：macOS 全量更新以完整 `.app` 为安装根目录

- 冻结版 macOS 更新助手的 `install_root` 必须使用 `RuntimePaths.install_root` 指向完整 `.app`，不能使用 `Contents/Resources/runtime`。
- `Contents/Resources/runtime` 只承载初始运行资源；全量更新必须在 `.app` 同级暂存候选 bundle，并以原子交换替换整个签名应用。
- 成功路径必须验证自动重启、事务确认、用户数据/Unix 权限保留和备份清理；失败路径至少覆盖旧 bundle 已移至 backup、候选替换失败后的恢复与临时目录清理。

## 2026-08-16：Hub 卡带的当前平台兼容 bootstrap 回退

### 背景

Hub index 与卡带资产可能在发布窗口中暂时滞后于新客户端 bootstrap。若旧 index/cache 中的卡带摘要仍有效、但该卡带只包含 Windows patch，macOS/SteamOS 客户端会优先选中它并在初始化时因平台不支持失败。

### 决定

卡带加载保留远端和 cache 的正常优先级；只有已选卡带不支持当前平台，并且同名 bootstrap 卡带通过解析且支持当前平台时，才选择 bootstrap。加载来源必须明确记为 `bootstrap-platform-fallback`。

### 影响

这是一条受限兼容性回退，不会无条件用 bootstrap 覆盖远端更新，也不绕过摘要校验。新增测试必须覆盖“旧 cache/index 有效但缺少当前平台、bootstrap 可用”的情形。

## 2026-08-16：VMware Windows 宿主上的 macOS 图形验收边界

### 背景

尽管 VMX 启用 3D、宿主使用 DX12 renderer，当前 macOS guest 仅暴露 VMware SVGA framebuffer，未暴露可供 P 社游戏建立 OpenGL pixel format 的图形加速能力。Stellaris 与 Hearts of Iron IV 的原版日志均在 `SDL_GL_CreateContext` / GL version 初始化处失败。

### 决定

将此环境作为 macOS 包安装、签名、客户端初始化、路径识别和更新机制的验收环境；不将其视为原版游戏图形运行通过的证据。若未来另立真实游戏内图形兼容性专项，该专项才需要使用具有可用 macOS OpenGL 图形加速的设备或环境；该要求不属于 `0.2.0` 发布验收。

### 放弃的做法

不为反复试错改动快照链、VMDK、Recovery NVRAM 或强制 Recovery 启动开关；这些路线已知可能破坏现有可启动 VM，且没有证据能补足该图形能力。

## 2026-08-17：PyInstaller onefile 子进程必须重置运行环境

### 背景

Windows frozen 全量更新失败后需要由延迟 helper 恢复旧 EXE。若恢复后的进程继承当前 onefile 进程的 PyInstaller 环境，它会继续引用父进程的 `_MEI...` 临时目录；父 helper 退出并清理该目录后，子进程可能在导入 `_tkinter` 等模块时失败。

### 决定

- 任何由 frozen 进程启动、且生命周期可能超过当前 onefile 父进程的 helper、确认进程、cleanup 进程或正常重启进程，都必须在子进程环境中设置 `PYINSTALLER_RESET_ENVIRONMENT=1`。
- 非 frozen 源码运行保持原环境，不无条件注入该变量。
- Windows frozen 回滚验收必须使用真实打包 EXE，验证恢复哈希、事务状态、坏版本标记、正常重启以及 helper/锁/失败文件清理；仅靠 monkeypatch 单元测试不足以证明句柄与 `_MEI` 生命周期正确。

## 2026-08-17：原生构建复制工作区不得携带陈旧模块版本

### 背景

SteamOS 复制工作区残留旧的 Git 忽略模块目录，首次构建把 `0.1.1`～`0.1.3` 一并打入候选包。Git 忽略目录不会被普通源码同步自动删除，因此远端工作区“覆盖解压”不等于发布输入干净。

### 决定

- 原生候选包构建前必须核对 `app/versions/` 的实际目录集合与计划维护基线。
- 对一次性复制工作区，可以只清理该复制目录下的 `app/versions/` 后重新同步受控基线与目标版本；不得在主工作区或用户真实安装目录中进行同类清理。
- 构建后必须检查归档内的模块版本集合，防止被 Git 忽略的历史目录污染发布包。

## 2026-08-17：统一问题记录与补丁完整性采用共享安全边界

### 背景

客户端和启动器此前各自展示异常，下载、补丁、更新、本地文件和程序内部错误容易混为“网络失败”；同时补丁二进制在下载、缓存或应用后可能被安全软件移动或修改，单靠下载完成状态不足以保证游戏目录安全。

### 决定

- 共享层统一使用 `ProblemReport`、`ProblemCode`、`ProblemSeverity` 和 `ProblemStore`；问题记录保存在 `data/problems/`，采用“一事件一 JSON”的原子写入，启动时保留最近 30 天且最多 100 条。
- 同一故障的安全重试合并到原事件并增加尝试次数；成功完成对应业务后自动标记解决，避免重复事件淹没问题中心。
- 问题文件只持久化固定动作 ID；动作在代码中通过允许列表解析，禁止从问题记录执行命令、脚本或任意 URL。
- 问题记录属于诊断副作用：存储失败必须记录日志，但不得把已经成功的下载、更新、回滚或模块加载结果改判为失败。
- 可执行补丁资源必须具备权威 SHA-256；无哈希的旧式数据可继续服务普通 DLC 兼容下载，但补丁二进制和补丁元数据拒绝进入应用流程。
- 补丁在下载提交、应用前和应用后均执行完整性检查；应用后文件缺失或哈希变化时，必须走既有事务恢复/原版恢复，不能让游戏文件停留在半修改状态。
- “疑似安全软件拦截”仅作为启发式分类，不武断归因 Defender。命中后停止该补丁工作流的无效自动重试、收束同批补丁任务，并要求用户核对来源和哈希后在系统安全界面手动处理。
- 程序不得关闭 Defender、自动添加排除项、自动恢复隔离文件或从问题记录执行任意 PowerShell；Windows 只允许打开固定的系统安全页面和 Microsoft 官方误报复检入口，其他平台隐藏 Windows 专属动作。

### 影响

后续新增可重放故障时，必须同时定义稳定错误码、阶段、用户摘要、脱敏上下文、允许动作和自动解决条件；新增补丁来源时必须先提供可验证的大小与 SHA-256，再允许应用。

## 2026-08-17：发布冻结显式排除未使用的 NumPy

### 背景

Windows 构建环境安装了可选的 NumPy/MKL，`PyInstaller --collect-all PIL` 会因构建机环境差异把未使用的 NumPy 依赖意外冻结，曾将启动器从约 17 MB 膨胀到约 173 MB、全量更新包膨胀到约 174 MB。项目源码不依赖 NumPy。

### 决定

- `tools/build_release.py` 与 `tools/build_native_release.py` 的 PyInstaller 命令统一显式加入 `--exclude-module numpy`。
- 构建测试必须断言 Windows 和原生发布命令都包含该排除项，避免换构建机或安装可选依赖后再次产生不可重复的大包。
- 若未来业务确实引入 NumPy，必须先评估各平台体积和运行依赖，再同时修改排除策略与回归测试；不能仅在某台构建机上临时删除包来掩盖问题。

## 2026-08-17：macOS 0.2.0 发布验收不包含游戏内运行

### 背景

当前无法取得能够正常打开 P 社游戏的 macOS 虚拟机或真实物理 Mac。现有 VMware 环境足以执行客户端下载、文件校验和补丁落盘验证，但缺少可用于 Stellaris、Hearts of Iron IV 等游戏的 accelerated 3D/OpenGL 能力。

### 决定

- macOS `0.2.0` 发布验收不再包含 Steam/Paradox Launcher 之后的真实游戏内运行、渲染或 DLC 解锁效果验证；这类验证不再是当前版本的发布阻塞项。
- macOS 原生包从当前源码重建后，验收退化为手动确认：DLC 文件可正常下载，文件大小与 SHA-256 符合预期，补丁可正常安装，补丁目标文件存在且权限与哈希符合预期。
- 必须验证补丁失败时能够恢复原文件；条件允许时再补充卸载/原版恢复流程确认。
- 发布说明、进度和交接文档必须明确写明“游戏内兼容性未纳入验收范围”，不得把退化验收表述为真实游戏兼容性通过。
- 2026-08-16 记录的 VMware 图形能力限制仍然有效，但“必须另寻具备图形加速的设备完成游戏内验收”不再作为 `0.2.0` 发布要求；未来若另立游戏兼容性专项，再单独准备合适硬件和验收计划。

## 2026-08-17：将项目上下文切换流程封装为项目技能

### 决定

- 新增项目技能 `.agents/skills/project-context-switch/SKILL.md`。
- 以后可通过 `/project-context-switch` 触发读取交接文档、核对 Git/测试状态、报告文档与真实工作区冲突的标准流程。
- 技能默认只做核对；若同条消息附带开发任务，仍必须在修改前先报告核对结果和冲突判断。

### 原因

避免每次切换上下文都重复粘贴长提示，同时保留 `AGENTS.md` 的工作区保护、测试核验和发布约束。

## 2026-08-17：上下文流程拆分为“进入”与“转出”两个自然语言技能

- `project-context-switch` 只负责新对话或新任务开始时的交接读取、Git/测试核对和改动前冲突报告。

- 两个技能均允许模型由自然语言意图自动触发；`/project-context-switch` 与 `/project-handoff` 只是可选简写，不是必需前缀。

## 2026-08-17：将本地提交与提交推送分为独立技能

- `commit-current-changes` 仅创建本地提交，绝不自动推送；对“进行一次提交”“提交当前改动”等自然语言生效。
- `commit-and-push` 只在用户明确要求“提交并推送”时使用；若改动涉及发布资产链路，必须先确认线上归档、更新包和清单已经上传并核验，避免触发 CI 恢复归档校验失败。
- 两个技能都禁止盲目暂存、强推、重写历史、绕过检查或覆盖其他用户改动。

## 2026-08-17：快速启动类技能遵循“动作优先”

- `run-current-client` 与 `run-current-publisher` 对单纯“运行/启动”请求必须在读取 Skill 后以首个工具调用直接执行 `Start-Process`，并立即返回 PID；不得预先读取项目文档、检查 Git 或入口、等待、轮询或运行测试。
- 仅当直接启动失败，或用户明确要求诊断、构建、测试时，才进入一次性诊断或对应的扩展流程。
- 上下文切换、交接、提交和推送技能保留其必要核对；这些属于安全与一致性门槛，不适用无条件的动作优先。

## 2026-08-17：原生库退出发布合同并进入持久保险库

- 新补丁 Release 只发布程序代理库和 AppInfo；历史 Release 中已有的原生库资产保留供旧客户端读取，新客户端忽略该资产。
- 游戏原生库属于当前用户安装的恢复资产，持久保存于 `context.paths.data/original-libraries/v1/`，不归入普通下载缓存，不受常规缓存清理或一键修复清理影响。
- 补丁运行期所需 `_o` 只能来自有效凭据匹配的保险库条目、有效凭据匹配的游戏目录 `_o`，或首次应用前可明确判定为原版状态的主库；不得从其他游戏、其他用户或发布端资源拼接。
- 游戏目录和保险库均无可信原生库时必须 fail-closed，保留当前文件并提示用户通过游戏平台验证游戏文件后重新采集。
- 一键修复使用 `repair_patch()` 和逐项 DLC 事务修复，不再执行 `reset()`、预先清空补丁文件或批量卸载 DLC。
- 持久修复日志用于程序中断后再次点击一键修复时从安全预检阶段幂等重放；当前不承诺程序启动后自动续作。
- 支持边界为 Windows x64、SteamOS x64、macOS Intel x64；本阶段不扩展 Apple Silicon 原生支持，也不改变代理库跨目录加载机制。

## 2026-08-17：发布器采用持久化受控发布批次与任务式导航

### 背景

发布器现有能力仍需保留，但界面按技术模块分散，且 UI 控制器同时承担线程、构建、上传、清单、验收与维护职责。三端原生构建边界已经明确，需要由 Windows 发布器负责候选汇总和统一发布，而不是继续扩展单体式“一键发布”控制器。

### 决定

- Windows 只汇总、校验和统一发布三端候选；Windows、SteamOS x64、macOS Intel x64 包分别在对应原生环境构建，不引入跨平台交叉构建。
- 发布器采用程序版本、游戏内容、Hub 与公告三类独立流水线，共享批次、预检、审计和恢复基础设施。
- 主导航采用“发布中心、内容与卡带、验收中心、高级维护”四区任务式结构。
- 正式操作采用持久化受控发布批次：自动执行可验证步骤，产生远端副作用前保留一次集中确认；重启后可从安全检查点恢复。
- GitLink/GitHub 两源所需数据包必须全部上传并回读核验后，才允许切换各自清单；游戏内容的 `catalog.json`、Hub/公告主表同样最后更新。
- 版本、平台、架构、包结构、哈希、三端一致性和双源配置等机器检查是不可绕过的硬门禁；人工验收仅可在紧急情况下填写原因后跳过，并写入批次审计。
- 单源发布、远程删除、采用远端附件和手动修复等低频或破坏性能力移入高级维护，保留二次确认与详细日志。
- 采用分阶段替换：先建立领域模型、批次存储、预检和编排接口，再迁移 UI 与各流水线；新路径达到测试对等前保留旧流程，不进行大爆炸重写。

完整实施计划见 `docs/publisher-refactor-plan.md`。


## 2026-08-17：高级维护授权必须绑定批次并由真实结果闭环审计

### 背景

远端删除、采用远端附件和单源发布会产生真实远端副作用。若无批次即可执行，或在输入确认文本时就记录“完成”，审计记录会与真实执行结果脱节。

### 决定

- 所有高级维护操作必须关联当前发布批次；无关联批次时拒绝执行，不允许绕过审计。
- 精确文本确认只生成一次性 `maintenance_authorized` 授权，不代表远端操作完成。
- 真实异步成功回调记录 `maintenance_completed`，真实失败回调记录 `maintenance_failed`；同一授权只能被消费一次。
- 安全暂停属于同一次已授权操作，暂停时保留授权，恢复后由最终结果完成审计。不可恢复失败会消费授权并清除恢复上下文；后续重新发起操作必须重新确认。
- 普通双源受控流水线不复用高级维护授权；单写者租约用于避免维护操作和其他发布副作用并发串扰。

### 影响

审计事件现在能够区分“已获准执行”和“真实执行结果”，且高风险入口不能脱离批次留下不可追溯的远端变更。


## 2026-08-17：发布批次只持久化非敏感目标摘要并显式处理验收与 schema

- 发布批次不得持久化远端凭据；服务层递归拒绝 token、password、secret、cookie、authorization、credential、private key、access/session key 等敏感字段，只保存执行与审计所需的非敏感目标摘要。
- 人工验收是可见的、仅供发布参考的软预检项；未完整通过时显示警告但不阻止确认或执行，确认审计记录验收结果、快照是否附加和 `acceptance_reference_only=True`。机器硬门禁仍不可绕过，验收快照变化仍会使预检和确认失效。
- 已知旧批次 schema 必须通过显式迁移升级并原子回写；未知 schema 必须 fail-closed，禁止按当前结构猜测加载。
- `degraded` 恢复必须以远端回读核验为依据：已经匹配的源不重复执行主表切换，只重试尚未完成或核验失败的源。

## 2026-08-18：发布器构建必须拒绝可选运行时膨胀

- 发布器声明的运行时依赖仅为 CustomTkinter 和 Pillow；构建时显式排除未使用的 `numpy`，防止 Pillow 的可选导入被 PyInstaller 误判为必须依赖，并将 Conda 的 MKL/OpenMP/MPI 原生运行时带入发行包。
- 发布器 EXE 先输出到 `build/publisher-artifact` 暂存目录，只有通过体积与归档标记检查后才替换 `dist/publisher/SignRiver-Publisher.exe`，因此异常构建不会覆盖上一份可用产物。
- 当前硬门禁为：EXE 不得超过 25 MiB，且不得包含 NumPy、Intel MKL、OpenMP target、Microsoft MPI 标记。将来若确有功能需要引入对应依赖，必须同步调整声明依赖、构建规则、体积上限与验证记录，不能静默放宽。

## 2026-08-18：未执行发布批次采用归档而非物理删除

- 为避免误建批次堆积，程序更新按“版本 + 收件目录”复用最新未执行批次，重复点击创建入口应直接打开原批次。
- 操作员可移除未执行草稿，但实现必须将批次移入发布工作区 `_archived`，保留事件日志和输入快照；不能以物理删除破坏审计线索。
- 仅 `draft`、`preflight_failed`、`awaiting_confirmation` 可归档。`running`、`paused`、`interrupted`、`degraded`、`failed`、`completed` 等批次保留在活动历史，以支持安全恢复和发布追溯。
- 面向操作员的历史与看板必须使用中文状态、下一步和文件摘要；内部批次 ID、枚举、字典参数仅作为排障辅助信息，不得作为主界面主体。

## 2026-08-18：发布器构建摘要必须以最终原始字节为准

- 禁止在为运行时标记做大小写归一化后再计算 SHA-256；标记扫描可使用小写副本，摘要必须始终对原始 EXE 字节计算。
- 发布器从暂存区复制到 `dist/publisher` 后，必须复验最终文件的体积、禁止运行时标记与 SHA-256，并要求其摘要和暂存产物一致；这样发布日志中的摘要才可直接用于附件校验和发布清单。
- CustomTkinter 控件参数必须以当前依赖版本支持的 API 为准；`CTkButton` 只能用 `anchor` 处理文本对齐，不得传入 Tk/Label 风格的 `justify` 参数。

## 2026-08-18：发布中心采用主页入口与页面内专项导航

- 发布中心的高频首页只承担“当前任务摘要 + 创建/打开批次 + 专项入口”，不再把收件、基线、预检、执行、单文件替换和批次详情并排堆在同一页。
- 专项操作使用同一 `ReleaseCenter` 容器内的 frame 切换（`grid_remove()` / `grid()`），而非 Tk 弹窗或第二个顶层窗口；每个专项页必须提供回到发布中心的明确入口。
- 历史批次选择应直接进入批次看板专项页，并将阅读空间优先留给详情（当前约 2:5），避免历史列表与长文本看板固定等宽导致不可读。
- 更新说明是可编辑的主要输入，应在“收件与准备”页占用独立、足够高的文本区；主页只呈现摘要，不能为节省空间截断操作员编写内容。
- 此改造只重排视图和导航，既有批次持久化、预检、冻结、归档、暂停恢复、远端基线和“人工验收仅参考”语义不得因 UI 重构改变。

## 2026-08-21：程序发布的预检与实际上传必须显式分两步

- “发布文件”入口只负责创建或复用本地发布记录、进入执行子页并运行预检；它不得隐式冻结输入或启动上传。
- 只有预检状态为 `AWAITING_CONFIRMATION` 时才启用“开始发布”。该按钮负责冻结输入并启动后台发布；预检失败必须禁用发布入口并保留错误信息。
- 暂停、异常中断、降级和失败后的恢复仍可使用执行页的同一主按钮；这不改变首次发布必须先完成预检、再由操作人显式开始的约束。

## 2026-08-18：发布中心历史栏固定且关闭先隐藏窗口

- 批次历史页的左栏是导航，不得随看板内容的最小请求宽度而变化；使用固定宽度（当前 360 px）和 `grid_propagate(False)`，详情区只使用剩余空间。不要恢复两个内容列同时按 weight 分配的布局，否则批次详情换行会导致比例抖动。
- 发布器允许退出时，先设置关闭标记并 `withdraw()` 根窗口，再停止 UI 事件泵和 `destroy()`；所有后台 UI 回调及上传进度投递必须同时检查关闭标记。这样既保留未恢复测试环境和后台发布的退出保护，也不会把控件销毁期间的中间布局暴露给操作员。

## 2026-08-18：发布器采用任务型工作区导航

- 发布器顶层导航应按操作员目标与风险边界组织，而不是按底层功能模块并列：固定为“发布工作台、内容准备、账号与发布目标、高级维护、核对与验收”。批次执行、进度和恢复只保留在“发布工作台”的执行面板中，不再占用重复的顶层入口。
- 同一程序更新批次的准备、远端基线、预检确认、执行与回读必须通过发布工作台的连续子页面承载；顶层“核对与验收 / 执行与恢复”只提供清晰入口与上下文跳转，避免复制发布状态或分裂批次逻辑。
- 人工验收始终是可附加的参考信息，不得升级为发布硬门禁；兼容发布、单源动作和远端修复始终标为高级维护，且不得与标准批次流程并行执行。

## 2026-08-18：发布仓库必须显式可见，且批次执行必须使用创建时冻结的目标

### 决策

发布器把 GitLink 与 GitHub 的 `owner/repository` 视为高风险、非敏感的发布合同：创建批次时写入 `ReleasePlan.remote_targets`，执行时只能从该冻结字段构造远端 provider；不得回退到随后可能已经改变的当前配置。令牌仍只在运行时从设置读取，绝不落入批次、看板或日志展示。

### 原因

“批次看板显示创建时目标、实际执行却读取当前配置”会造成操作员看到的仓库与写入的仓库不一致。2026-08-18 的测试演练误发正式资产库事件暴露了该风险：双源发布如果仅显示“GitLink / GitHub”，操作员无法在确认前可靠辨认实际仓库。

### 实施约束

- 顶层必须有“账号与发布目标”可见页，逐端展示配置 owner、精确仓库、URL、凭据是否已配置；令牌不得渲染。
- 发布主页、批次看板与确认摘要必须逐端显示 `owner/repository`。未创建批次时显示下一批次的配置目标，已创建批次时标明冻结目标。
- 缺失或不完整的冻结目标一律拒绝执行，提示重新创建批次；不得用当前设置补全旧批次。
- “配置的所有者”不能表述成令牌经过远端认证的身份；本地页面只反映将被使用的配置，远端身份验证属于另一个明确操作。
- 改动发布目标后必须重新创建批次。任何删除、回滚或补发远端 Release 都属于独立的高风险远端写入，必须单独获得用户授权。

## 2026-08-18：上传进度由 Provider 上报、服务层以同一批次实例持久化

- GitHub / GitLink 的网络层已有字节级回调；provider 负责将其标准化为 `(source, artifact, sent, total)`，发布服务负责计算实时速度并保存 UI 所需的非敏感状态，界面不直接接触网络回调或凭据。
- 进度回调必须更新正在由 orchestrator 执行的同一 `ReleasePlan` 实例，不能在回调中 `get()` 一个新实例后 `save()`；后者会与编排器的阶段状态写入竞争并可能覆盖状态。
- 持久化应节流（当前约每秒最多 5 次，完成时强制写入），字段仅限源站、文件名、已传输字节、总字节、速度与时间。不得持久化上传 URL、Authorization header、token 或任何本地发布凭据。
- 单文件字节传输完成不等于发布完成：后续远端回读、SHA-256 与清单校验必须用独立文案说明，不能伪装成上传进度。

## 2026-08-18：DLC / 补丁的常规发布统一进入 `GAME_CONTENT` 批次

- **决策**：DLC、补丁、AppInfo 与最终 `catalog.json` 的常规双源发布，必须由当前游戏的 `workspace.publish_files(profile)` 取得验证后的完整本地输出，创建 `GAME_CONTENT` 批次后从发布工作台执行。
- **原因**：逐文件上传和手选 `catalog.json` 使关联文件散落在多个页面，容易遗漏文件、误切换索引、误选目标或重复创建批次；批次流水线可冻结目标并保留远端基线、预检、确认、进度、安全暂停、恢复与归档审计。
- **边界**：内容准备页仅负责导入、构建、查看本地输出和跳转流水线；兼容发布页仅保留高级维护/回退能力，不再作为普通内容发布的单源入口。相同游戏、Release 标签和输出目录的未执行批次应复用，避免重复批次。

## 2026-08-20：DLC / 补丁发布按冻结目标确保仓库存在

- `GAME_CONTENT` 的远端差异读取和上传前，必须对创建时冻结的 GitLink/GitHub 目标执行“存在即复用、不存在则创建”。这使“加入上传队列”能够从空白的目标仓库开始，不要求操作人预先手动建库。
- GitHub 通过 API 按配置的个人账户或组织创建公开仓库；GitLink CLI 的创建命令无法指定所有者，因此仅在其当前登录账户与冻结目标所有者一致时允许自动创建，否则明确停止并提示切换账户或手动建库。不得为了便利把资源写入未核验的同名仓库。
- 此自动建库范围仅限 DLC / 补丁资源；程序更新与模块归档仍要求其发布仓库预先存在，避免将发布目标配置错误扩大为新的远端资产库。

## 2026-08-20：不再提供兼容发布 / 单源发布工作区

- 标准双源发布已经覆盖 DLC/补丁、程序更新、模块归档和卡带中心；Steam 数据刷新被资源构建流程覆盖，远端维护也已按资源类型归位。因此发布器不再暴露“兼容发布（回退 / 修复）”或单源发布入口。
- 旧实现可暂时保留为未接线代码，避免与正在进行的发布器模块拆分交叉；但不得重新在 UI 中添加入口。若未来确有单源恢复需求，应设计为有明确目标、风险说明和单独授权的新流程，而不是恢复旧综合页面。

## 2026-08-18：日常账号配置必须独立于高级维护

- GitLink / GitHub 的当前发布目标属于日常可见、可编辑的账号工作区，不得仅在只读摘要后跳转到“高级维护”。
- 账号页仅呈现仓库坐标、仓库地址和凭据是否已配置；令牌始终不得回显、打印或持久化到批次。
- 在账号页修改 owner / repository 时必须保留现有令牌，并明确告知该修改只影响新建批次；已创建批次必须继续使用其冻结目标。
- 高级维护仅保留兼容发布、远端维护及其他低频、高风险能力，不承担日常账号配置。

## 2026-08-18：模块化发布器的跨工作区运行时能力归入 `ui_runtime.py`

- 窗口关闭保护、单写者协调和滚动列表重置属于跨工作区运行时能力，应由 `ui_runtime.py` 提供，不能依赖某个历史巨型 UI 文件。
- 发布器 UI 的测试应聚合 shell 与相关 mixin 源码，验证实际组合后的行为；不得把“实现必须位于单个 `ui.py` 文件”当作架构约束。
- 顶层导航顺序以操作频率与风险边界为准：发布、准备、目标确认、维护在前；批次执行仅位于发布工作台内；不阻塞发布的核对与验收固定在最后。

## 2026-08-18：远端核对属于批次看板的上下文操作

- “读取远端基线 / 查看结果 / 导出 JSON”依赖当前选中的发布批次，因此不再作为发布工作台的独立页面或工作流目的地。
- UI 应将该只读操作放在批次看板内，与冻结的发布目标、批次状态和历史记录一并展示；未选中批次时禁用操作，导出仅在已存在基线时开放。
- 保留服务层的 `capture_remote_baseline` 与 `export_remote_baseline` 行为和只读边界；本决策仅改变 UI 承载位置，不改变远端交互语义。

## 2026-08-18：游戏选择属于内容发布作用域，而非发布器顶层状态

- 当前游戏仍以 `self.profile` 为唯一事实来源，但选择控件固定放在“内容准备 → DLC / 补丁发布包”页面；不得再在发布器标题栏增加第二个全局游戏下拉框。
- “发布工作台”的 DLC / 补丁入口只负责进入游戏作用域明确的发布包页面，不应直接静默创建内容批次。实际创建/复用批次必须由该页面的明确按钮触发。
- 批次创建后继续冻结其游戏、Release 标签和远端目标；后续切换 `self.profile` 不得重写任何历史批次。

## 2026-08-18：客户端设置页采用紧凑单列分组与设置行

- 客户端“设置”页保持既有顶部、侧栏、色板、圆角与单列阅读方式，只重组内容区；不得为设置页另起一套视觉语言或为了填满页面改成复杂双栏。
- 设置项按关系聚合到少量组卡片中，当前固定为“下载与网络”“程序与存储”“常规设置”；组内使用左侧名称/说明、右侧控件的设置行与细分隔线，避免每个功能各占一张大卡片。
- 主要行动（例如检查更新、开始测速）可保留强调样式；清理、打开目录等辅助操作必须弱化，开关应放在设置行右侧。业务控件实例名和事件处理需保持稳定，以避免仅因视觉重排破坏现有设置持久化与异步状态更新。

## 2026-08-18：客户端游戏选择使用按需出现的可搜索浮层

- “游戏检测”主卡片中的当前游戏控件保持紧凑的下拉式外观，不在主页面长期增加搜索框，也不改造顶部、侧栏或整体色板。
- 选择行为由同风格、短生命周期的 `CTkToplevel` 承载：搜索框和固定高度可滚动列表仅在用户点击当前游戏时出现；支持列表变多时不能撑开主页面。
- 搜索统一对选择名、展示名和 `game_id` 做不区分大小写匹配，以兼容中文、英文名称和未来卡带索引的命名变化；当前选择必须有可见状态，未匹配时需要给出自然空状态提示。
- 游戏切换仍必须进入既有 `_select_game()`，以保留下载/安装活动时禁止切换、远端卡带惰性加载和错误恢复的保护；不得为新选择器复制或绕开业务切换逻辑。
- “导出支持列表”属于辅助能力，应保留但采用次级描边/浅色视觉，不得与启动游戏等主要操作竞争注意力。


## 2026-08-18：活动发布目录必须选择性同步，三端发行包必须原生重建

- `app/versions/0.1.0/` 是 Git 跟踪的客户端规范基线，但 `app/versions/<发行版本>/` 可能包含尚未回流到基线的发行期业务修复；本轮 `0.2.0` 已包含问题中心与补丁健壮性等较新逻辑，不能用基线整目录覆盖活动目录。
- 在构建活动版本前，应把已验证的基线改动按文件与行为选择性移植到目标版本目录，并单独编译目标入口；覆盖前应保留工作目录外的临时备份或可靠差异记录。仅构建 `0.1.0` 不等于发行包已包含最新 UI。
- 卡带或补丁配置发生字段迁移时，也必须先用启动器的隔离模块加载方式验证活动版本；若活动版本仍采用旧内部模型，优先在解析边界增加“新字段优先、旧字段回退”的最小兼容映射，禁止仅因启动失败就整目录覆盖活动版本运行时。
- Windows、SteamOS、macOS 的最终冻结包只能在对应原生平台构建。Windows 产物完成不代表三端完成；若其他平台包早于目标活动目录，应明确标为过期候选，禁止据此生成三端更新清单或进行发布。
- 虚拟机来宾没有合法 SSH / 远程执行通道时，不得猜测密码、读取私人凭据或改变虚拟机安全配置以强行接管；应把原生构建标为外部阻塞，等待用户提供受控接入或人工协作。

## 2026-08-21：所有单目录 DLC 统一使用通用外层 ZIP 校验

- 群星与钢铁雄心4等游戏的发布附件均是“一个受管理 DLC 顶层目录”的外层 ZIP；目录中的 `.dlc`、内嵌 ZIP、缩略图和资源树都属于游戏自身读取的载荷，而非客户端安装器必须单独解析的发布格式。
- 新发布的群星卡带与发布器工作区统一使用 `package_inspector=directory`。通用校验继续验证 SHA-256、ZIP 安全性、唯一顶层目录和管理编号；下载器提供正式附件名时必须核对完整 `dlcNNN_name.zip` 格式。
- 旧的 `stellaris_zip` 卡带标签继续被客户端接受，但映射至通用目录校验，以兼容已经下载/缓存的旧 Hub 卡带，不能因一次卡带更新造成客户端启动或下载失败。
- 离线恢复路径可使用 `dlcNNN.zip` 这类历史短临时名；仅在没有可信附件名且短名符合该严格格式时，才从已安全验证的顶层目录恢复编号。任意名称（如 `bad.zip`）不得借此绕过名称校验。

## 2026-08-21：当前发布目录是内容入队的唯一凭据

- `.build-complete.json` 只保留为构建后的诊断快照，不能再作为上传队列的第二份必需凭据；它被清理、失效或来自旧工作区都不得阻断一份当前完整的发布目录。
- 加入队列时直接校验发布目录的必需 AppInfo / 补丁文件、DLC 分卷完整性、单文件大小与当前 SHA-256，并在随后生成 `catalog.json`。源目录在构建后发生变化不会隐式改写已构建产物；若需要包含源变更，用户仍应重新构建。
- GitLink 元数据 GET 请求允许有限重试以抵御短暂网络波动；创建、更新、删除等写请求绝不自动重试，避免不确定网络结果造成重复发布。

## 2026-08-22：卡带平台可用性由云端资源状态决定

- 游戏的 `patch_platforms` 只声明客户端可解析的平台变体，**不**代表对应 Release 已上传可用资源；客户端主表另行使用 `platform_resources` 表示已发布的补丁/DLC 状态。
- 当前平台的卡带可用条件是 `patch OR dlc`，因此补丁-only 与 DLC-only 都是合法状态；内置 DLC 游戏不能因 `dlc=false` 被隐藏。
- 旧发布器 profile 没有明确状态时，只能由成功发布记录保守导出 Windows 可用性；SteamOS/macOS 需要维护者明确确认，禁止由本地构建目录或平台声明推断。即使直接调用主表构建工具而跳过工作区导出，也只能使用 Windows 兼容回退，不能依据 `patch_platforms` 推断原生云端资源。
- 报错指南的可执行工具遵循平台过滤、HTTPS、非空下载和用户确认执行；不使用签名链、证书链或额外哈希发布合同，以控制单人维护复杂度。

## 2026-08-22：一键排错与按需修复工具采用分层、多端渐进策略

- “一键排错”是客户端内置的、非破坏性检查入口：只收集网络、游戏目录、磁盘空间、近期问题记录及适用补丁状态，不直接修改游戏文件、系统设置或网络配置。
- 所有平台保留同一组通用检查；补丁状态检查仅在当前游戏已声明当前平台补丁字段时启用。Windows 可随客户端逐步加入更多本地检查，SteamOS 与 macOS 优先保留少量简单、可靠的通用检查和适用补丁检查，不以功能数量强行对齐。
- “修复工具”不内置在一键排错的自动操作中：一键排错负责发现问题，报错指南负责解释现象和给出下一步；需要工具时，按当前平台筛选后让用户按需下载并明确确认执行。Windows 专用脚本不得在 SteamOS/macOS 显示，shell 工具只在 SteamOS/macOS 显示。
- 工具下载维持最小安全边界：HTTPS、合法文件名、非空内容和临时文件原子替换；不额外引入签名链、证书链或复杂发布哈希合同，以保持单人维护可持续。

## 2026-08-22：报错指南内容必须按适用范围与可验证性筛选

- 旧《群星》报错资料不得直接作为多游戏事实；后续内容先按“通用、Hub/DLC 工作流、游戏/启动器特化、一键排错、排除/待验证”分层，并为每项保留来源和验证状态。
- 程序只承接官方 Steam、已支持游戏、系统环境和 Hub 自身链路；学习版、联机加速器、SteamCMD/创意工坊下载流程不进入未来指南候选。
- 一键排错只能执行可判定的非破坏性只读检查，异常必须跳转到固定指南；不得自动修改游戏、系统、防护或网络设置。Windows 显示、Documents、运行库和安全软件问题默认仅作为指南/研究项。
- 未来按游戏显示的指南需要游戏 ID、平台、前置条件和验证状态；当前仅按 `platforms` 过滤的云端指南模型不足以安全承载这些内容。
- 完整来源盘点、候选结论、检查设计和未来字段建议见 `docs/error-guide-content-catalog.md`；该文档不等同于已实现功能。

## 2026-08-23：报错指南通过 Hub Release 维护，附件只下载不执行

- 报错指南运营内容固定放在发布器本地工作区 `publisher-workspace/guides/`，由 `guides_index.json`、详情 JSON 和扁平 `assets/` 组成；发布器复用既有 `hub` Release 导出和双源发布通道，不增加独立指南 Release、单独上传队列、在线编辑器、签名或哈希发布合同。`config/guides/` 仅保留首批低风险文章的出厂离线兜底版本。
- 远程指南必须以稳定 `guide_id` 覆盖同 ID 的出厂正文，避免重复卡片；平台继续仅使用既有 `platforms` 过滤，游戏特化内容不因本次资源管道而放入全局指南。
- 指南附件使用工具条目的 `asset_name` 引用同一 hub Release 的附件，文件名必须是平铺且唯一的名称。发布器仅校验 JSON 根对象、索引详情存在、附件存在和资源重名；未配置指南目录不是发布阻断，配置了但引用缺失时才明确阻止本次 hub 生成。
- 客户端附件操作的安全边界收紧为“用户确认 → 下载到指南缓存 → 打开所在文件夹 → 用户自行查看/处理”。即使历史数据含 `run_mode`，客户端也不得自动运行 PowerShell、CMD、Shell 或未知可执行文件。首批上线文章不包含脚本或修复工具。
