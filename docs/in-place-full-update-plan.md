# 原地全量更新实施计划

> 状态：设计草案 v1  
> 日期：2026-07-25  
> 关联文档：[模块化更新架构](./update-architecture.md)

## 1. 目标

将 `kind: "full"` 的发布从“打开下载页、由用户手动切换目录”升级为原地更新：在既有安装目录中安全替换启动器及其运行时文件，同时保留用户数据和 DLC 缓存。

更新完成后，用户仍从原来的快捷方式和安装路径启动程序；不需要重新发现游戏、重新下载已经校验过的 DLC 包，或重新配置下载源。

## 2. 范围与边界

### 2.1 可替换内容

- 发行启动器 EXE；
- `app/` 中的宿主状态与应用模块；
- 出厂默认配置和随发行包提供的静态资源；
- 由发行包清单显式声明的其他运行时文件。

### 2.2 必须保留的内容

- `data/`：SQLite 数据库、用户设置、日志、安装回执和诊断文件；
- `cache/`：已下载且可复用的 DLC、补丁和卡带缓存；
- 用户覆盖配置，例如本地维护的更新源、令牌或路径配置；
- 未列入发行包清单的用户文件。

全量包不得将整个安装目录删除后重建，也不得以空目录覆盖 `data/` 或 `cache/`。

## 3. 设计原则

1. 运行中的 EXE 不自我替换。当前启动器只负责准备更新；退出后由独立助手进程执行文件交换。
2. 可恢复优先。任何替换前都保留可回滚的旧文件，并将事务状态原子写入磁盘。
3. 所有权明确。助手仅处理发行清单声明的受管路径，绝不按目录递归删除未知文件。
4. 内容先验证再切换。下载包、解压目录和发行文件清单均在改动安装目录前验证。
5. 启动确认收尾。新启动器成功加载应用模块后才确认事务并清理备份；失败则自动恢复。

## 4. 发行包与清单

### 4.1 完整包格式

全量更新包使用 ZIP，根目录为发行文件布局，不包含 `data/` 与 `cache/`。包内必须包含：

- 启动器 EXE；
- `app/`；
- `config/defaults/`（仅出厂默认值，不直接覆盖用户配置）；
- `release-manifest.json`。

`release-manifest.json` 至少声明 schema 版本、发行版本、每个受管文件的相对路径、大小和 SHA-256。构建工具从实际产物生成该文件，更新助手不能信任 ZIP 内未列入清单的文件。

### 4.2 更新清单扩展

现有 `full` Release 保持 `package_url`、`sha256`、`size` 和 `min_launcher_version`。新增可选字段：

- `installer_version`：更新助手协议版本；
- `mandatory`：是否阻止用户继续运行旧版本；
- `notes`：更新说明。

当 `installer_version` 高于当前启动器可支持的版本时，回退为打开下载页，不尝试本地覆盖。

## 5. 更新事务

### 5.1 准备阶段（主程序）

1. 检查安装目录可写、没有其他更新事务、磁盘空间满足“新包解压 + 受管旧文件备份”的上限。
2. 下载完整包至 `cache/updates/*.part`，验证大小与 SHA-256。
3. 解压至安装目录同卷的 `.update-staging/<transaction-id>/`，执行 ZIP 安全检查、发行清单校验和文件摘要校验。
4. 创建 `data/update/transaction.json`，记录事务 ID、旧/新版本、阶段、受管文件清单、暂存路径、备份路径和助手命令。
5. 启动独立更新助手，传入安装根目录和事务 ID；主程序退出。

### 5.2 替换阶段（更新助手）

1. 等待主程序 PID 退出，并确认安装根目录未被其他更新助手锁定。
2. 将当前受管文件逐个移动到 `.update-backup/<transaction-id>/`；每步追加事务日志。
3. 从暂存目录逐个原子移动新文件到目标位置；只允许发行清单中的路径。
4. 写入阶段 `swapped`，启动新的发行启动器并传递 `--confirm-full-update <transaction-id>`。
5. 若替换中断或任一步失败，按反序恢复已移动的旧文件，并记录可诊断错误。

### 5.3 确认或回滚阶段（新启动器）

1. 新启动器读取待确认事务，验证自身版本、`app/state.json` 和当前应用模块可加载。
2. 成功时写入 `confirmed`，清理暂存目录；备份目录延迟到下次健康启动或保留期结束后删除。
3. 失败时启动恢复助手，按备份恢复受管文件；恢复后重新启动旧启动器。
4. 若恢复也失败，保留备份和事务日志，显示明确的修复路径，禁止静默删除任何文件。

## 6. 配置策略

将当前混合 `config/` 拆分为两类：

- 发行默认配置：随全量包更新，例如 `config/defaults/update.json`、出厂卡带；
- 用户覆盖配置：首次运行时写入 `data/config/`，后续全量更新不覆盖。

读取顺序为“用户覆盖 > 发行默认 > 内置默认”。迁移时保留现有 `config/update.json` 的有效值，避免全量更新清空用户设置的下载源或网络选项。

## 7. 故障处理

| 场景 | 处理 |
| --- | --- |
| 下载或校验失败 | 不启动助手，保留可删除的临时包，旧版本继续运行。 |
| 解压或发行清单校验失败 | 删除暂存目录，不触碰安装文件。 |
| 主程序未退出 | 助手超时退出，事务保持 `prepared`，下次可重试或取消。 |
| 文件交换失败 | 立即按已完成步骤回滚，保留备份和日志。 |
| 新版本初始化失败 | 自动恢复旧启动器及受管文件，并将新版本标记为失败。 |
| 断电或被强制终止 | 下次启动检测未确认事务，继续确认或进入恢复流程。 |

## 9. 验收标准

- 全量更新后，原安装路径和快捷方式仍可启动新版本。
- `data/` 与 `cache/` 的文件内容、时间戳和路径均保持不变。
- 用户更新源、网络设置和游戏路径在更新后仍生效。
- 更新包摘要不匹配、恶意 ZIP 路径、发行清单不一致时，安装目录完全不变。
- 替换前、替换中、替换后确认前分别模拟进程终止，均可自动恢复至可启动状态。
- 新模块初始化失败时自动回到旧启动器和旧模块，且不会重复提供该失败版本。
- 重复执行同一全量更新是幂等的，不损坏缓存、数据或备份。
- Windows 10/11 的安装目录、桌面快捷方式、中文路径和受限写权限场景均通过冒烟测试。

## 10. 非目标

- 本期不实现跨盘安装目录迁移。
- 本期不清理 DLC 缓存，也不改变 DLC 缓存键。
- 本期不将启动器自更新混入普通 `module` 更新路径。
- 清单签名仍应作为后续安全升级；在此之前继续强制 HTTPS、大小、SHA-256 和严格发行文件清单校验。
