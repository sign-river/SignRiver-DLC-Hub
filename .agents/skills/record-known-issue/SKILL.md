# SignRiver DLC Hub：记录已知问题

当用户的请求以 **“记录：”** 或 **“记录:”** 开头，且后续内容是在描述一个需要后续统一处理的缺陷、体验问题或功能需求时，默认使用本技能。`/record-known-issue` 只是可选简写。

本技能的目标是把问题可靠地写入 `docs/known-issues.md`，而不是立即实现、修复、清理缓存、删除文件、构建或发布。

## 记录流程

1. 先按项目规则读取交接文档并核对分支、HEAD 与 `git status --short`。不要重置、覆盖或清理用户已有改动。
2. 阅读 `docs/known-issues.md`，检查是否已有同一问题：
   - 已有条目：补充现象、复现信息或期望行为，避免重复编号；
   - 新条目：使用下一个连续的 `KI-XXX` 编号。
3. 需要核实实现或上下文时，只做最小范围的源码/配置检索。涉及客户端问题时，读取 `app/state.json` 的 `active_version` 并记录实际活动版本；不得写死版本号。
4. 在“待处理”下记录清楚：状态、优先级、发现日期、影响范围、现象或需求概述、复现条件（适用时）、当前原因或待确认原因、期望行为、计划修复版本和验收要点。
   - 缺陷默认状态为“待排期”；尚未设计的新增能力默认状态为“需求待设计”。
   - 优先级应根据用户描述的实际影响谨慎判断；不确定时使用 `P2`，不要夸大为阻断问题。
   - 对截图、日志或用户描述，只记录可证实的结论；未知根因必须写“待确认”。
5. 在 `docs/agent/HANDOFF.md` 用简短条目记录本次登记、是否修改运行时代码/缓存/活动模块，以及实际执行的验证。一次性问题不要写进 `AGENTS.md` 或 `DECISIONS.md`。
6. 对文档执行 `git diff --check`。仅文档改动时不必运行 pytest，但必须明确标注未运行。
7. 按项目提交约定，只精确暂存本次问题清单和交接文档，并创建一个本地 Git 提交；绝不自动 `git push`。

## 范围与边界

- “记录：”默认表示**先登记、暂不修改功能**。只有用户在同一请求中明确要求实施，才在记录后另行执行实现工作。
- 如果用户描述的是已发生的运行异常，可说明它与客户端“问题记录中心”不同：这里记录的是开发排期用的产品/工程问题。
- 不在问题清单中写密码、令牌、账号、私有下载凭据或大段原始日志；日志应概括关键错误和复现条件。
- 不把未验证的猜测写成根因，也不宣称问题已修复。

## 完成报告

向用户简要说明：问题编号、登记文件、已确认或待确认的原因、验证结果、本地提交，以及“未推送”。
